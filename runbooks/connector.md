# 고객 커넥터

커넥터는 `connector/`에 있는 별도 프로그램이다. 우리 게이트웨이에 먼저 연결하고, 로컬 카운터에 별도 서비스 키로 전달한다. 카운터의 개인 키 검사·admission·지표와 중앙 개인 키/사용량 역할을 구분한다. 질문·답변은 Kukie 게이트웨이를 통과하므로 고객 내부에서만 처리된다고 안내하지 않는다.

## 전제

등록된 Kubernetes 클러스터, 설치 권한, 내부 카운터와 모델이 필요하다. DNS·지정 Kukie 목적지 HTTPS 443 및 응답, 장시간 WebSocket Upgrade/재연결이 가능해야 한다. NAT/방화벽/회사 프록시 경로는 고객 환경에서 준비한다. 공개 고객 도메인·인바운드 포트는 요구하지 않는다.

Kotlin 관리자의 커넥터 등록/회전 API가 반환한 원문 자격과 내부 카운터 서비스 키를 각각 파일로 마운트한다. 원문을 values나 CLI 인자에 적지 않는다. 중앙 DB에는 커넥터 자격 SHA-256만 저장한다. 자격은 24시간 뒤 만료되므로 만료 전 회전·파일 갱신이 필요하다. 자동 갱신·Helm 전달은 DURO-203에서 연결한다. 기존 개인 API 키를 커넥터 자격으로 쓰지 않는다.

```sh
./connector \
  --gateway https://<Kukie 연결 호스트>/connector/v1/connect \
  --cluster-id <등록된 클러스터 ID> \
  --credential-file /var/run/connector/credential \
  --counter-url http://<카운터 Service>.<namespace>.svc:8080/v1 \
  --counter-credential-file /var/run/counter/service-key \
  --workers 4
```

고객 클러스터/계정/모델 주소를 기본값으로 가정하지 않는다. 카운터 주소는 관리자 로컬 설정에서만 받으며 요청이 바꿀 수 없다. 사설 CA는 `--ca-file`로 추가한다. 인증서 검증을 끄는 옵션은 없다. 회사 프록시는 gateway 접속에 HTTPS_PROXY/NO_PROXY를 적용할 수 있으며 로컬 카운터에는 환경 프록시를 사용하지 않는다.

## 실패와 자격 회전

워커 1~8개를 유지한다. 연결당 하나씩 전달하고 성공 연결은 재사용한다. 끊긴 추론은 재실행하지 않으며 유휴 연결만 1~30초 backoff+jitter로 재시도한다. 재접속 때 자격 파일을 다시 읽고, 카운터 서비스 키는 매 호출 다시 읽는다. 잘못된 자격/파일은 연결되지 않은 상태로 재시도한다. 초기 구성 오류는 원문/주소를 포함하지 않는 메시지로 종료한다.

게이트웨이는 중앙 등록을 5초마다 조회(요청 제한 5초)해 회전/폐기·만료를 반영하며, 해당 세션과 진행 요청도 닫는다. 고객 사용자가 취소하면 WS 단절→커넥터 context 취소→카운터→vLLM으로 전파한다. 단절을 성공 응답으로 간주하지 않는다.

상세 wire 계약은 [게이트웨이 프로토콜](https://github.com/durokukie/kukie-serving-gateway/blob/main/docs/connector-protocol.md)의 v1을 따른다. 서로 다른 저장소의 호환성은 게이트웨이 `scripts/test-connector-e2e.sh`에 이 저장소 경로를 주어 실제 커넥터·기존 카운터와 가짜 모델로 시험한다. Kubernetes/운영/GPU를 호출하지 않는다.

## 미적용

아직 이미지 태그/차트 릴리스, Helm 자동 설치, 대시보드 모달, 운영 라우팅, 자격 자동 갱신을 하지 않았다. 기존 카운터·오븐·포털을 변경하거나 종료하지 않는다. 이 모듈 추가만으로 원클릭 설치 완료를 의미하지 않는다.


## 모델 준비 보고 (DURO-205)

커넥터는 kukie.connector.v2를 우선 협상하고 v1 서버와도 연결한다. v2에서만 15초 주기로 카운터 /v1/model-status를 서비스 키로 조회해 model_status 프레임을 보낸다. v1/구형 카운터는 준비 확인이 없는 상태이며 등록 모델을 준비된 것으로 추정하지 않는다.

카운터는 설정된 upstream에 GET /v1/models를 보내 정확한 모델 id가 있는지 확인한다. 추론·GPU 기동은 하지 않는다. 프록시/redirect/개인 키 전달은 없으며 모델 최대 100개·동시 검사 8개·전체 3초·개별 2초·응답 64 KiB로 제한하고 결과를 15초 캐시한다. 동시 갱신 요청은 503으로 거절한다. 준비 확인은 순간적인 응답 가능성만 확인하며 용량/추론 성공을 보증하지 않는다. 상태 응답에는 내부 주소·자격을 넣지 않는다.

진행 추론의 응답 쓰기를 상태 프레임이 지연시키지 않도록 해당 연결이 유휴일 때만 보고한다. 모든 연결이 오래 바쁘면 상태가 만료되어 확인 필요로 바뀔 수 있으며 추론 실패로 추정하지 않는다.

갱신은 호출자 취소와 분리한 3초 기한을 사용한다. 전체 모델을 검사하지 못하면 503을 반환하고 이전 캐시의 확인 시각을 갱신하지 않는다. 확인 시각은 참고값이며 신선도는 캐시 경과 시간(ageMs)과 커넥터 조회 왕복 시간으로 전달해 고객 장비의 시계 오차에 의존하지 않는다.

같은 커넥터 프로세스의 워커는 관측 캐시를 공유해 상태 조회를 한 번만 수행한다. 카운터 캐시의 기한/경과 시간에는 monotonic 시각을 유지하고, 출력하는 참고용 checkedAt만 UTC로 변환한다.
