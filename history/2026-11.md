## 2026-11-11 1층 Helm 이전 준비: 조사와 dry-run (DURO-166·DURO-167, 설치 전)

kukie-gpu에 손으로 올린 1층(DCGM exporter, Kukie 읽기 RoleBinding, NVIDIA 장치 플러그인)을 릴리스 `kukie-gpu`로 옮기고 preflight를 처음 켜기 위한 조사다. **클러스터는 바꾸지 않았다.** 읽기 명령, `helm upgrade --dry-run=server`, `kubectl diff --server-side`, `kubectl apply --server-side --dry-run=server`만 썼다. 실제 이전은 오븐 RBAC를 namespace Role로 좁히는 차트 `0.13.0`(DURO-179)과 함께 helm upgrade 한 번으로 한다. 절차는 `runbooks/gpu-view.md` "kukie-gpu: 손 apply한 1층을 릴리스로 옮기기".

**지금 상태.**

**새로 생기는 것과 이미 있는 것.** `dcgm`·`rbac`·`preflight` 켬(장치 플러그인은 켠 경우·끈 경우)을 지금 릴리스 렌더와 비교했다.

| 리소스 | 클러스터 | 판정 |
| --- | --- | --- |
| DaemonSet `gpu-metrics/dcgm-exporter` | 있음 | 소유 표시만. 필드 차이·충돌 없음 |
| RoleBinding `gpu-metrics/kukie-gpu-metrics`, `llm/kukie-gpu-metrics` | 있음 | 소유 표시만. 차이·충돌 없음 |

| Service `gpu-metrics/dcgm-exporter` | 없음 | 새로 생김 |

- 비교 방법: 렌더한 네 리소스를 `kubectl diff --server-side --field-manager=helm`에 넣었더니 차이가 없었고(종료 코드 0), `kubectl apply --server-side --field-manager=helm --dry-run=server`도 충돌 없이 통과했다. 그래서 지웠다 다시 만들 것은 없고, Pod 템플릿이 같아 DaemonSet Pod도 다시 뜨지 않는다.
- 이미 있는 ClusterRole `kukie-gpu-metrics`·`kukie-gpu-reader`와 ClusterRoleBinding `kukie-gpu-reader`는 kukie-infra GPU 읽기 RBAC 것이다. 차트는 RoleBinding으로 묶기만 한다.

**dry-run.** `helm upgrade --reset-then-reuse-values --set dcgm.enabled=true,rbac.enabled=true,preflight.enabled=true,devicePlugin.enabled=<true|false> --dry-run=server`(저장소의 `0.12.0` 차트).
- 소유 표시 없이: 두 경우 모두 `RoleBinding "kukie-gpu-metrics" in namespace "gpu-metrics" exists and cannot be imported into the current release`로 멈췄다. Helm은 첫 충돌에서 멈추므로 목록은 하나만 나온다. 나머지 충돌 대상은 위 표의 "있음" 줄이다.
- `--take-ownership`을 더하면 두 경우 모두 통과했다(revision 18, `pending-upgrade`). 실제 이전은 겹치는 것이 넷뿐인지 다시 확인하려고 `--take-ownership` 대신 손으로 소유 표시를 붙인다.

**preflight를 실제로 돌릴 수 있는지.**
- 이미지 `alpine/kubectl`(Docker Hub): Job은 GPU taint를 허용하지 않아 일반 노드(`t3.large` 2대)에 뜬다. 그 노드들은 이미 NAT로 ghcr.io·public ECR 이미지를 받고 있고, 같은 날 GPU 노드가 Docker Hub의 `vllm/vllm-openai`(약 9.2GB)를 받았다. 받을 수 있다고 본다. Docker Hub 익명 요청 한도는 이 한 번으로는 문제가 안 된다.
- 권한·namespace: 차트가 만드는 것만 쓴다. `gpu-metrics`의 Pod 목록(Role `kukie-gpu-preflight-dcgm`), 노드·StorageClass·CSIDriver 읽기(ClusterRole), `kukie-gpu`의 테스트 PVC와 결과 ConfigMap. 미리 만들어 둘 것은 없다.
- 결과 위치: 설치 namespace `kukie-gpu`의 ConfigMap `kukie-gpu-preflight`. runbook의 `gpu-metrics`는 옛 가정이라 고쳤다.
- 예상: `gpu` 실패(GPU 노드 0대), `driver` 건너뜀, `huggingface` 통과, `storage` 건너뜀(`ebs-csi-default-sc`가 `WaitForFirstConsumer`, CSI 드라이버 `ebs.csi.aws.com` 있음), `permission` 건너뜀 → `1/2 통과`. 테스트 PVC는 만들지 않는다.

**장치 플러그인.** 손 apply와 차트가 모두 `v0.20.1`(같은 digest)이고 렌더가 같다. 옮겨도 Pod가 다시 뜨지 않고, GPU 노드가 없으면 Pod 자체가 없다. 그래서 차트로 옮기는 것을 추천한다(`devicePlugin.enabled=true`). 고객 설치 경로와 같은 모양으로 우리 클러스터를 돌리고, 손으로 둔 것이 없어진다. 대신 릴리스를 지우거나 이전 revision으로 되돌리면 함께 지워지므로, 그때는 GPU 노드가 0대일 때 하고 바로 손 apply로 다시 올린다.

**꼭 고쳐야 할 차트 문제는 찾지 못했다.** 생각해 볼 점만 남긴다.
- 되돌리기(`helm rollback`)가 옮겨 온 리소스를 지운다. 장치 플러그인처럼 지워지면 곤란한 것에 `helm.sh/resource-policy: keep`을 둘지는 따로 정한다.
- 기본값 `namespaces.create=true`로 설치한 클러스터는 uninstall 때 `gpu-metrics` namespace가 지워진다(`llm`만 오븐을 켜면 keep). kukie-gpu는 `false`를 유지한다.

**확인 못 한 것.** preflight의 실제 실행, 소유 표시 뒤의 실제 upgrade, GPU 노드가 있을 때의 `driver` 검사.

## 2026-11-13 kukie-gpu pull Secret 제거 (DURO-213)

11-11에 패키지를 공개로 바꾼 뒤에도 kukie-gpu의 카운터·오븐·커넥터는 비공개 시절 pull Secret `ghcr-pull`(개인 classic PAT, 2027-02-09 만료)을 달고 있었다. 만료되면 공개 이미지도 받지 못할 수 있어 연결을 뺐다.

- 릴리스: `helm upgrade kukie-gpu oci://ghcr.io/durokukie/charts/kukie-gpu --version 0.14.1 --reset-then-reuse-values --set-json 'counter.imagePullSecrets=[]' --set-json 'oven.imagePullSecrets=[]'`. 서버 dry-run 비교에서 바뀐 것은 두 Deployment의 `imagePullSecrets`뿐이었다. revision 23, 카운터·오븐 새 Pod Running.
- 커넥터: kukie-gpu-infra `kubernetes/dev-serving/connector.yaml`에서 한 줄을 빼고 apply. 새 Pod가 자격 갱신 후 게이트웨이 세션 4개를 다시 열었다.
- 확인: Secret 없이 `imagePullPolicy: Always`로 띄운 시험 Pod가 다른 노드에서 카운터 이미지를 새로 받았다(664ms). 시험 Pod는 지웠다.
- Secret `ghcr-pull`을 지웠다(값은 읽지 않았다). kukie-gitops-test에는 복사본이 없었다.
- 사용자는 GitHub에서 그 PAT을 지워도 된다.
